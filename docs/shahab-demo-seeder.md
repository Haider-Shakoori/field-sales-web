# Shahab Kabul Demo Seeder

The Shahab demo dataset is intentionally opt-in because it is large.

## Run

```bash
php artisan migrate
php artisan db:seed --class=Database\\Seeders\\ShahabDemoSeeder
```

Alternatively set:

```dotenv
SEED_SHAHAB_DEMO=true
```

before running the normal `DatabaseSeeder`.

## Seeded scale

- 4 Shahab operational sales zones in Kabul, each built as a MultiPolygon from its member district boundaries
- 22 Kabul municipal district territories using the public ArcGIS Kabul Districts GeoJSON layer
- 4 sales managers
- 4 supervisors, each explicitly assigned to report to one sales manager
- 52 salesmen, each assigned under the relevant supervisor
  - 11 non-route salesmen per zone
  - 2 routed salesmen per zone
- 8 sales routes
- 200 customers per district (4,400 total)
- Direct salesman assignment for every customer
- Near-equal customer distribution among the 13 salesmen in each zone
- 100 completed visits per salesman in the most recently completed week (5,200 visits)
- 20 Shahab FMCG products and a retail price list

## Demo geography and contact-data rules

The seeder downloads the public ArcGIS **Kabul Districts** layer at seed time. That layer exposes 22 polygon features and GeoJSON output. Territory `polygon` values are stored as the returned GeoJSON Polygon/MultiPolygon geometry, and each zone geofence is assembled from the real district geometries assigned to that zone.

Customer coordinates remain synthetic demo shop locations, but they are generated **inside the corresponding district polygon** rather than around a rectangular approximation.

The seed therefore requires outbound HTTPS access to the ArcGIS service. If all 22 district geometries are not returned, the seeder fails instead of silently falling back to fake territory boundaries.

Names are synthetic Afghan male demo identities. Phone values use an Afghanistan-style placeholder pattern generated by the seeder. They are not scraped contacts and should not be treated as verified real-person phone numbers.

Historical visit records reference inactive seeded devices so the one-active-device policy does not block a salesperson from signing in on a real demo phone.
